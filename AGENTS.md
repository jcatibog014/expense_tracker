# AGENTS.md

This file guides AI coding agents (Claude Code, Codex, Cursor, Copilot and others) working in this repository.

## Overview

**Ang Gastos!**, a personal expense tracker in Python (Flask). The repo is `expense_tracker` and the Python package is `gastos`. It records income, spending and transfers between wallets, sorts them into categories, and totals them by month. It also has budgets, repeating entries, CSV import/export, a dashboard with charts, and yearly reports (the roadmap is `docs/PLAN.md`). It is a learning project for **SQL, aggregation, dates and charts**, so all database access is raw SQL (no ORM). Keep the code readable for a learner: short comments that explain *why*, and no extra libraries unless the owner asks for them. Write the README in simple (A1-level) English.

Python 3.13 is at `%LOCALAPPDATA%\Programs\Python\Python313\python.exe`. Use the virtual environment:

- Install: `.venv\Scripts\python -m pip install -r requirements.txt` (create `.venv` with `python -m venv .venv` first if it's missing).
- First time: `.venv\Scripts\flask --app gastos init-db`, then `.venv\Scripts\flask --app gastos create-user <name>`.
- Run: `.venv\Scripts\flask --app gastos run --debug --port 5002`, then open http://127.0.0.1:5002. (Port 5002: Swap Meter uses 5000, Ambon Alert 5001.)
- Test: `.venv\Scripts\python -m pytest`. Tests use a fresh SQLite file each and never use the internet. Set `TEST_DATABASE_URL` to an **empty** Neon branch to run the same tests on PostgreSQL (each test drops and remakes the tables).
- Other commands: `set-password <name>`, `reset-demo`, `init-db --yes` (deletes everything).

## Architecture

- **Two databases, one SQL.** `gastos/db.py` connects to SQLite (`instance/gastos.sqlite`, git-ignored) or, when `DATABASE_URL` is set, to PostgreSQL with psycopg (Neon on the live site). Use `db.query()`, `query_one()`, `execute()`, `execute_many()`, `insert()` (for `INSERT ... RETURNING id`) and `commit()`. Rows come back as dicts. Write `?` placeholders; `_sql()` turns them into `%s` (and `%` into `%%`) for psycopg. Never put values into the SQL text. Nothing is saved without `commit()`; the connection closes at the end of each request.
- Keep SQL portable: dates are `'YYYY-MM-DD'` text and months are `substr(date, 1, 7)`; there is no `strftime()`/`to_char()`. True/false is `0/1`. Use `RETURNING id`, `ON CONFLICT`, `COALESCE`, `CASE`. In `schema.sql`, `id INTEGER PRIMARY KEY` is rewritten for Postgres by `schema_sql()`, so keep that exact spelling.
- `gastos/schema.sql`: `users`, `accounts` (wallets), `categories`, `recurring`, `transactions`, `budgets`. Money is **integer centavos**. A transaction's `kind` is `income`, `expense` or `transfer`; a CHECK makes transfers have `to_account_id` and no category, and the others the opposite. A wallet or category that is still used can't be deleted (FOREIGN KEY), so the app archives it. `UNIQUE (recurring_id, date)` makes posting a recurring item safe to repeat.
- **Privacy:** every table except `users` has `user_id`, and every query must filter on `g.user["id"]`. A row of another user must give 404. Tests check that the demo can't see the owner's data.
- `gastos/auth.py`: login/logout (`/login`, `POST /logout`), `POST /demo`, `/settings` (change password), `login_required`, `g.user` (`id`, `username`, `is_demo`), and the CLI commands. No sign-up page. Usernames are lower-cased. Wrong logins say the same `WRONG_LOGIN` whether or not the user exists; 5 wrong passwords lock the account for 15 minutes (`failed_logins`, `locked_until`). Login starts a fresh session (`log_in()`), and `safe_next()` only allows paths on this site.
- **CSRF:** every POST form needs `<input type="hidden" name="csrf_token" value="{{ csrf_token() }}">`; `check_csrf()` refuses others with 400. Tests use `post()` from `tests/conftest.py`, which sets the token.
- **The demo** is the user with `is_demo = 1` (username `demo`, a random password nobody knows). `demo_user()` makes it on first use and calls `seed.reset_demo()` when `demo_reset_at` is over an hour old. The demo can't change its password.
- `gastos/seed.py`: `DEFAULT_ACCOUNTS`/`DEFAULT_CATEGORIES` for every new user (`add_defaults()`), and `demo_transactions(today)`, 6 months of Metro Manila-style sample money dated relative to today. It is deterministic per date (`random.Random(today.isoformat())`).
- `gastos/dates.py`: `today()`/`now()` are in Philippine time (`PH_TIME`, a fixed UTC+8, because Windows has no tz database without the `tzdata` package and the PH has no daylight saving). There are also month helpers (`add_months`, `day_in_month`, `month_label`, ...).
- `gastos/money.py`: `peso(centavos, signed=False)` (also the Jinja filter `peso`), `parse_amount(text, allow_negative=False)` (typed text → centavos via `Decimal`, or `None`; max `MAX_CENTAVOS` ₱10M so it fits a Postgres INTEGER), `amount_input()` (centavos → the text a form box shows).
- `gastos/validation.py` must not import Flask. `validate_transaction(form, accounts, categories, today)`, `validate_account(form, taken_names)` and `validate_category(form, taken_names, kind=None)` return `(data, errors)`; `read_filters(args, today)` reads the entries list's URL (bad values are ignored, no `month` = this month, `month=all` = every month). The caller passes the wallets/categories this user may pick as `{id: row}`, so an id from another user is just "Choose a wallet". `CATEGORY_COLORS` are names (`blue` … `red`, `gray`).
- `gastos/queries.py` holds the SQL that reads and adds up money: `month_totals`, `recent_entries`, `find_entries`/`filtered_totals` (both built by `filter_sql()`, which joins fixed SQL pieces and puts every visitor value in `params`; LIKE search puts `\` before `\`, `%` and `_`), `wallet_balances` (opening balance + correlated sub-queries; transfers count out of one wallet and into the other), `category_usage`. `ENTRY_SELECT` is the shared SELECT with the wallet/category names. Transfers never count as income or spending.
  - Dashboard/report SQL: `month_totals(user_id, first_day, until=None)` (`until` is an exclusive end date, used for "September 1–28"), `monthly_totals(first_month, months)` (`GROUP BY substr(date, 1, 7)`; Python fills empty months with 0), `spending_by_category(first_day)` (this month and last month in one pass with `SUM(CASE ...)`; `HAVING` keeps categories spent this month), `running_spending(first_day)` (window function `CAST(SUM(SUM(amount)) OVER (ORDER BY date) AS BIGINT)`; the CAST stops Postgres returning a Decimal), `category_month_grid(year)` (GROUP BY category and month, pivoted in Python), `biggest_expenses`, `month_entries`.
  - Budget SQL: `budget_rows(first_day)` (every spending category with its budget or `None` and the amount spent; `b.month = ?` is in the LEFT JOIN's `ON` on purpose; archived categories show only with a budget), `save_budget()` (upsert `ON CONFLICT ... DO UPDATE SET amount = excluded.amount`; `None` deletes), `copy_budgets()` (`INSERT ... SELECT ... ON CONFLICT DO NOTHING`, returns how many were added).
- `gastos/recurring.py`: `due_dates(day_of_month, start, end, until, after=None)` and `next_due()` are pure date maths; a day past the month's end moves to its last day (`dates.day_in_month`). `next_date(item, today)` gives a row's next date. `post_due(user_id, today)` inserts the entries due since `posted_until` (or `start_date`) up to today, with `ON CONFLICT (recurring_id, date) DO NOTHING`, then sets `posted_until = today`, so an added entry that the user deleted is not added again. The caller commits. `upcoming(user_id, today, days=14)` gives `[(date, item)]`.
- `gastos/csv_io.py` (no Flask, no SQL). The columns are `HEADERS` (`date, type, amount, wallet, to_wallet, category, note`).
  - `export_csv(entries)` starts with a UTF-8 BOM for Excel. Text cells go through `safe_cell()`, which puts `'` before `= + - @` (CSV/formula injection); `unsafe_cell()` takes it off again on import.
  - `parse_import(text, wallets, categories, today, create_missing)` checks every row. It accepts header and type aliases, `;` files, and dates as `YYYY-MM-DD` or `MM/DD/YYYY`. It returns rows `{line, data, errors}`, plus `new_wallets` and `new_categories` (only names that good rows use) and a whole-file `error`.
  - `mark_duplicates()` counts matches against saved entries (`entry_key()`), so 3 identical rows vs 2 saved = 2 duplicates.
  - `decode()` tries UTF-8 and falls back to cp1252.
  - Limits: `MAX_FILE_BYTES` 400 KB and `MAX_ROWS` 2000; the demo has `DEMO_MAX_ROWS` 200.
- `gastos/charts.py` (no Flask, no SQL): `budget_status(budget, spent)` (percent, left, `state` ok/warning (≥ `WARNING_PERCENT` 80)/over (spent > budget), width capped at 100), `change()`, `kept_percent()`, `month_columns()`, `running_lines()` (+ `fill_days()`: carries totals over empty days; `None` after today so the line stops), `category_bars()` (share % and width % of the biggest), `heat_level()` (0..`HEAT_LEVELS`=4), `average()`. Chart JSON is `{labels, titles, series: [{name, color, values}]}` with values in centavos and `color` a CSS variable name.
- `gastos/views/`: one blueprint per area. `views/__init__.py` has `owned_row(table, id)` (this user's row or 404). `main.home` (`/?month=YYYY-MM`, bad or missing = this month) is the dashboard. It has 4 stat tiles: income and spending, each with the change since last month (for the current month, compared with the same days of last month), left over + % kept, and money in wallets. Below them are spending by category (HTML bars), the day-by-day line, 12-month columns, the month's latest entries and the wallets. The dashboard also has a Budgets card (fullest first) and "Coming up" (repeating entries in the next 14 days). `budgets.index` (`/budgets?month=`) is one form with a box per category, named `budget-<id>` (empty or 0 = no budget); `POST /budgets/copy` copies last month's. `recurring` (`views/repeating.py`, `/repeating`) has list, new, edit and delete (no transfers). Deleting an item keeps its entries (`recurring_id` → NULL), and an edit counts from now on. Its `post_due_entries()` is a `before_app_request` that runs `post_due()` for the logged-in user on every request and flashes what it added. It must run after `auth.load_user`, so the blueprint order in `create_app()` matters. `data` (`views/data.py`, `/data`) is the CSV page.
  - `GET /data/export` takes the entries filters and returns `queries.export_entries()`, oldest first.
  - Import is two steps. `POST /data/import` uploads the file and shows a preview without saving anything. The preview form carries the file text in a hidden `<textarea name="csv_text">`. `POST /data/import/confirm` parses and checks it all again, creates the missing wallets (kind cash) and categories (gray), and inserts with `execute_many`.
  - `MAX_FORM_MEMORY_SIZE` is 1 MB, so that text fits in the form.
  - Names are only looked up among the user's own wallets and categories. The Entries page has "Download CSV" (same filters) and "Import CSV"; Settings links here too.

`reports.index` (`/reports?year=`, clamped to 2000..next year) has year totals, the average spending a month (over the months so far; all 12 for past years), a month-by-month chart + table, the category × month heat table and the 5 biggest expenses. `transactions` (`/transactions`; the old `/entries…` addresses redirect there with 301): list with filters, month arrows and paging (`PER_PAGE` 50), `/transactions/new` (`?kind=`; "Save and add another" keeps kind, date and wallet), `/transactions/<id>/edit` (the kind tabs switch with `?kind=`), `POST /transactions/<id>/delete`. Forms carry a `back` URL (checked by `safe_next()`). `choices()` leaves out archived wallets/categories, except the ones the entry already uses. `wallets` (`/wallets`) and `categories` (`/categories`): list, new, edit, `POST .../archive` (toggles), `POST .../delete` (only when unused, counted in `transactions` and `recurring`; otherwise a message says to archive). A category's kind can't change after it's made.
- Templates: `_macros.html` has `input()`, `select()` (options are `(value, label)` pairs, built in the view because Jinja has no `zip`), `amount()` and `entry_row()`. Category dots use `class="dot cat-{{ color }}"`.
- `gastos/__init__.py`: `create_app(test_config)`, config from env (`SECRET_KEY`, `DATABASE_URL`, and `RENDER` makes cookies HTTPS-only and requires a real `SECRET_KEY`), and error pages (`error.html`).

### Front end

- Server-rendered Jinja pages with plain HTML forms; they work without JavaScript. `static/app.js` only adds extras: the theme toggle (it fires a `themechange` event), `data-confirm` ("Are you sure?" before a form sends), and the charts.
- **Charts:** Chart.js 4.4.7 from jsDelivr, loaded only by pages with charts (`{% block head %}{% include "_chartjs.html" %}`), pinned with `integrity`. Use the static `dist/chart.umd.js`, not jsDelivr's generated `.min.js`, which must not be used with integrity. `_charts.html` has `chart(kind, data, label, height, table_open)`, used with `{% call %}` to pass the table twin, and `change_line()`. A chart is a `<figure class="chart" data-chart="columns|line">` with a `<canvas>`, its JSON in `<script type="application/json" class="chart-data">` (via `tojson`) and a `<details>` "Show as table". `drawCharts()` reads the colours from CSS variables and draws again on `themechange` and on a system theme change. Without Chart.js it opens the tables instead; without JS the chart area is hidden (`.js` class on `<html>`).
- Chart rules (dataviz skill): bars ≤ 24px with a 4px rounded end and a square base; lines 2px with an end dot that has a ring in the card colour (`pointBorderColor` must be the line colour elsewhere, or the legend/tooltip keys vanish). There is a hairline grid, no dashes, and one y-axis with compact ₱ ticks. A tooltip shows every series (value first), and the line chart has a crosshair plugin. A legend appears for 2+ series, and every chart has a table. Spending by category is plain HTML bars in one colour (`--chart-current`), sorted, with names and values written; it is not a doughnut.
- DOM text goes in with `textContent`, never `innerHTML`.

## Conventions

- Brand: "Ang Gastos!" (`APP_NAME` Jinja global, the `<title>`s, and the header `Ang <em>Gastos!</em>`, where `Gastos!` is `--bar-accent`). The header shows no logo image: `static/icons/logo.svg` (a notebook page with a ₱) is only the browser-tab and home-screen icon. The user-facing word is **"transactions"** (not "entries"); code names like `entry_row` and `.entry` stay.
- Header: an ink-blue bar (`.site-header`, `--bar*` tokens in all three colour blocks, text ≥ 4.5:1). It holds the brand, the theme button, the username, Log out (`.button-on-bar`) and the 6 tabs from the `tabs` list in `base.html`: Dashboard, Transactions, Budgets, Reports, Wallets, Settings. The active tab has a `--bar-accent` underline. On phones the tabs are a 3 × 2 grid. Settings (`auth.settings`) is a hub linking to Categories, Repeating and CSV files, plus the password form. Pages under it (`categories`, `recurring`, `data` blueprints) light up the Settings tab and get a "‹ Settings" `back-link`.
- Page layout: every page starts with `.page-title` (the `<h1>` + its main button), then, if it has one, a `.month-nav` row (‹ `<h2 class="month-title">` ›). Use sentence case for headings and buttons. The login page is one column with the demo card under the login card.
- Theme "ledger notebook": cream paper with ruled lines (`body` background), `.card` with a red margin line (`::before`), ink-blue text, `--income` green and `--expense` red. Fonts: Kalam (headings, brand) and Source Sans 3 (body), from Google Fonts; amounts use `tabular-nums`.
- Styling: `static/style.css`, colours as CSS variables on `:root`. Dark mode ("night ledger") redefines them under `prefers-color-scheme: dark` (unless `data-theme="light"`) and under `[data-theme="dark"]`; change both blocks together. The phone breakpoint is 520px.
- Accessibility: text ≥ 4.5:1 and `--control-border` ≥ 3:1 against `--paper` and `--card` in both themes. Touch targets ≥ 44px. Form errors use `aria-invalid` + `aria-describedby`.
- Category and chart colours: `--cat-*` CSS variables, the dataviz skill's 8 categorical colours in their fixed order plus gray, with separate dark-mode steps (validated against `--card` in both themes). Three light ones are under 3:1, so a colour always has its name next to it. Don't use them for text. Chart tokens: `--chart-income` (blue) and `--chart-spending` (orange), because red/green failed the colour-blind check; `--chart-current` (blue) and `--chart-context` (gray, for "last month"); `--chart-grid` and `--chart-axis`; and `--heat-1..4`, a one-hue blue ramp: light steps 150–300, dark steps 700–550. Text on every step is ≥ 4.5:1. Re-run the validator if you change any of them.
- Demo data: `seed.demo_transactions()` tops up Cash/GCash from the Bank when they can't pay, so no demo wallet goes below zero (`test_demo_wallets_never_go_below_zero`). `reset_demo()` also makes `DEMO_RECURRING` items (`posted_until` = today) and links the matching demo entries to them, and adds `DEMO_BUDGETS` for every demo month. Keep `DEMO_RECURRING` in step with the fixed entries in `demo_transactions()`.
- Budget meters (`budget_meter()` in `_macros.html`): blue → `--status-warning` from 80% → `--status-critical` when over. These are the dataviz status colours, the same in both themes. The track is the fill colour at 20% (`color-mix`). The state is also written in words with an icon (✕ over, ! almost), so it never relies on colour.
- Schema changes: there are no migrations yet. Until the live database exists, change `schema.sql` and run `init-db` (it deletes all data, so check `instance/gastos.sqlite` for real users first).
- Show money with the `peso` filter. Income is `amount-income` (green, "+"), spending is `amount-expense` (red, "−").
- Keep comments teaching-oriented but brief. Add or update a test with every behaviour change.
- **Screenshots:** README screenshots live in `docs/screenshots/` and are taken as the demo user with `docs/take_screenshots.py` (Playwright + Edge; install Playwright separately, it is not in requirements). Add new pages to its `PAGES` list, and retake the screenshots whenever a page changes visibly.
- **Security headers** (`security_headers()` in `create_app`): a Content-Security-Policy (`CONTENT_SECURITY_POLICY`), `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, and HSTS on Render.
  - Scripts may only come from `'self'` and cdn.jsdelivr.net. **No inline `<script>`** (`test_no_inline_scripts`), which is why the early theme code is `static/theme-init.js`, loaded without `defer` in `<head>`. JSON in `<script type="application/json">` is fine.
  - Styles allow `'unsafe-inline'` because of `style="width: …"` on bars and meters.
  - A new outside resource needs a CSP change.
- Icons: `static/icons/logo.svg`, plus PNGs (`icon-32`, `apple-touch-icon` 180, `icon-192`/`512` on a paper tile with 14% padding, maskable) made by `docs/make_icons.py`. Re-run it when the logo changes. `static/site.webmanifest` is served as `application/manifest+json`, and `test_app_manifest_and_icons` checks every linked icon exists. The theme button has two inline SVGs (`.icon-moon`/`.icon-sun`); CSS shows one.
- **Deploy:** Render + Neon.
  - `render.yaml` defines Render service `ang-gastos` (free, Singapore): `gunicorn "gastos:create_app()" --workers 2`, `healthCheckPath: /healthz` (no login, no database), `SECRET_KEY` generated, and `DATABASE_URL` (`sync: false`; the owner pastes Neon's pooled connection string).
  - On Render, `create_app()` refuses to start without a real `SECRET_KEY` or a `DATABASE_URL`.
  - Tables and the owner's login are made once from the owner's PC with `DATABASE_URL` set (`init-db`, `create-user`); see the README. The demo user makes itself.
  - psycopg connects with `prepare_threshold=None` (Neon's pooler).
  - The owner does the Neon/Render steps. Once it is live, don't rename the service: Render would build a second one. Never run `init-db` against the live database again; it deletes everything.
- Git: one branch + PR per stage of `docs/PLAN.md`. On this Windows machine, pass commit messages and PR bodies as files (`git commit -F`, `gh pr create --body-file`).
